구현 설명 (How it works)

ytdown — 이 앱은 어떻게 만들어졌나

ytdown이 실제로 어떻게 구현됐는지(현재 코드 기준) 따라가는 문서입니다. PLAN.md가 무엇을 만들고 어떻게 배포하는지를 다룬다면, 이 문서는 동작하는 앱이 어떻게 맞물려 돌아가는지 — 요청 흐름, 각 파일의 역할, 설계 결정 — 를 설명합니다.

앱은 React + TypeScript 단일 페이지 UI(Vite로 빌드)와 작은 TypeScript Node 서버로 이루어집니다. 서버는 yt-dlp 명령을 실행하고, 진행 로그를 브라우저로 실시간 스트리밍하며, 완성된 파일을 내려줍니다. 다운로드 규약 자체는 기존 vanilla 버전과 동일하고, UI와 서버의 언어/빌드만 바뀌었습니다.

1. 큰 그림

브라우저 (React SPA) ──POST /api/download {url,format}──▶ Node 서버 (server.ts, 127.0.0.1)
   ▲                                                          │ spawn("bash", [download.sh, …])
   │  실시간 로그 (스트리밍 응답 본문)                          ▼
   │                                                      download.sh ──▶ yt-dlp + ffmpeg
   │                                                          │            → downloads/<제목>.<확장자>
   └──GET /api/file/<name> (첨부)◀──────────────────────────────┘  마지막 줄 "__FILE__ <name>" = 결과

요청 하나가 전체 작업을 처리합니다. 서버는 yt-dlp의 출력을 실행되는 즉시 HTTP 응답으로 흘려보내고, 그 스트림의 마지막 줄이 표식(sentinel)입니다 — 성공이면 __FILE__ <name>, 실패면 __ERROR__ <message>. 브라우저는 스트림을 실시간으로 읽다가, 마지막 줄을 파싱해 결과를 판단합니다.

브라우저는 유튜브와 직접 통신하지 않습니다 — 오직 서버만(스크립트를 통해) 통신합니다.

개발 vs 운영이 새로 생긴 한 가지 차이입니다(§6 참고): 개발에서는 Vite가 React 앱을 핫리로드로 서빙하면서 /api/*를 Node 서버로 프록시하고, 운영에서는 Vite가 앱을 dist/로 빌드하면 같은 Node 서버가 그 정적 파일 과 API를 함께 서빙합니다.

2. 파일 구조

ytdown/
├── index.html             # Vite 진입점: 빈 <div id="root"> + 모듈 스크립트
├── src/
│   ├── main.tsx           # <App/> 을 #root 에 마운트
│   ├── App.tsx            # UI 전체: 상태, 폼, 스트리밍 fetch
│   ├── App.css            # 스타일(라이트/다크)
│   └── types.ts           # 공유 타입 (Format = "mp3" | "mp4")
├── server/
│   └── server.ts          # 백엔드: 라우팅, 검증, spawn, 스트리밍, 정적/파일 서빙
├── download.sh            # 내 yt-dlp 명령 — 유일하게 커스터마이즈하는 파일
├── vite.config.ts         # React 플러그인 + 개발 프록시 (/api → 127.0.0.1:5174)
├── tsconfig.json          # 프런트엔드 TS 설정
├── tsconfig.server.json   # 백엔드 TS 설정 (타입체크용; 실행은 tsx)
├── package.json           # 의존성 + 스크립트 (dev / build / start)
├── dist/                  # Vite 빌드 산출물 (gitignore)
└── downloads/             # 결과 파일 (gitignore)

이제 빌드 단계와 node_modules(React, Vite, TypeScript)가 생겼습니다. 그 비용의 대가로: 타입이 있는 컴포넌트 기반 UI와 개발 중 핫리로드를 얻습니다.

3. 프런트엔드 (React + TypeScript)

3.1 진입점: index.html → main.tsx

index.html은 거의 비어 있습니다 — <div id="root"></div>와 <script type="module" src="/src/main.tsx">뿐. main.tsx가 그 div를 찾아 앱을 마운트합니다:

createRoot(document.getElementById("root")!).render(
  <StrictMode><App /></StrictMode>,
);

!는 TypeScript의 non-null 단언(root div는 항상 존재). StrictMode는 개발에서만 동작하며 일부 로직을 두 번 실행해 버그를 드러냅니다.

3.2 상태: App.tsx

UI는 컴포넌트 하나. 화면에서 바뀔 수 있는 모든 값은 React 상태(useState)입니다 — 상태를 set 해야 React가 다시 그리기 때문입니다. 일반 변수는 바뀌어도 화면이 갱신되지 않습니다.

상태이유
url입력창 값(controlled input)
format: Format"mp3" | "mp4" — 잘못된 값은 컴파일 단계에서 막힘
busy버튼 비활성화 / "Downloading…" 표시
log스트리밍 진행 텍스트, <pre>에 표시
status{ kind: "ok" | "err"; text; file? } | null — 결과 줄

format은 types.ts의 Format union을 써서, 라디오가 유효한 값만 설정하게 합니다.

3.3 제출 핸들러 — 같은 스트리밍 규약을 React로

handleSubmit은 네트워크 스트림을 await 하므로 async입니다. 순서:

  1. e.preventDefault() — 폼이 페이지를 새로고침하지 않게(SPA니까).
  2. 상태 초기화(busy=true, log/status 비움).
  3. fetch("/api/download", { method:"POST", body: JSON.stringify({ url, format }) }). !res.ok(400/429)면 본문 텍스트를 읽어 예외로 던짐.
  4. 스트림 본문을 조각씩 읽기 — res.body.getReader() + TextDecoder, for (;;) 루프에서 done이면 break, 각 조각을 log에 누적해 실시간 표시.
  5. 누적 텍스트를 표식과 매칭: __FILE__ <name> → "ok" 상태 + 자동 다운로드; __ERROR__ <message> → 예외.
  6. catch가 모든 실패를 "err" 상태로 모음(err instanceof Error로 unknown에서 메시지를 안전하게 추출).
  7. finally가 항상 버튼을 다시 풀어줌.

JSX는 조건부로 렌더합니다: {status && …}는 결과가 있을 때만, {log && <pre>…}는 로그가 있을 때만 표시. 표식 규약은 이전과 동일하고, DOM 갱신만 이제 React 상태를 거칩니다(수동 document 조작 대신).

4. 서버 (server/server.ts)

순수 node:http, 이제 TypeScript(컴파일 없이 tsx가 직접 실행). 127.0.0.1 에만 바인딩하여 네트워크에서 직접 닿을 수 없습니다 — VPS에서도 nginx가 공개 면을 담당합니다.

4.1 라우팅

메서드 & 경로핸들러역할
POST /api/downloadhandleDownload검증, 작업 실행, 로그 스트리밍
GET /api/file/<name>handleFile완성 파일을 다운로드로 스트리밍
GET <그 외>serveFrontenddist/의 빌드된 SPA 서빙

4.2 한 번에 한 작업

모듈 레벨 let busy = false가 다운로드를 직렬화: 작업 중이면 429 거부, 자식 프로세스의 error/close에서 다시 풀어줌. VPS RAM이 2GB이고, 직렬 작업이 스트리밍 로그를 깔끔하게 유지합니다.

4.3 요청 검증

  • url — isValidYouTubeUrl()이 new URL()로 파싱(틀리면 throw하므로 try/catch)하고 https: 그리고 호스트 화이트리스트(youtube.com, www./m./music.youtube.com, youtu.be)를 요구. raw is string 타입 가드라서, true를 반환한 뒤 TS가 url을 string으로 좁혀줌.
  • format — 정확히 "mp3" 또는 "mp4".

검증은 무엇을 spawn하기 전에 끝납니다. 본문은 4KB로 제한(작은 JSON만 기대).

4.4 다운로드 실행 + 로그 스트리밍

  1. 실행 전 downloads/의 파일 이름들을 Set(before)에 기록 — 끝난 뒤 새 파일을 찾기 위함.
  2. 200 + text/plain + no-cache를 먼저 보내고 응답을 실시간 로그 채널로 열어둠.
  3. 스크립트 실행 — 의도된 두 가지: 
    const child = spawn("bash", [SCRIPT, url, format, DOWNLOADS_DIR], { cwd: PROJECT });
    • 인자 배열, 셸 문자열 아님 → url이 별도 인자라 셸 보간이 없고 명령 주입 불가.
    • bash <script>로 실행 → exec 비트와 무관하게 shebang과 set -o pipefail 적용.
  4. child.stdout/stderr를 res.write(d)로 응답에 흘려보냄 — 실시간 로그.

종료 시: error → __ERROR__; 0이 아닌 종료 → __ERROR__ download failed; 종료 0 → before와 비교해 새 파일들 중 mtimeMs 최신(newestFile()의 for…of)을 골라 __FILE__ <name>로 끝냄. 이 "새 파일 차집합"이 yt-dlp의 보고 없이 결과 파일명을 알아내는 방법입니다.

4.5 SPA와 완성 파일 서빙

  • serveFrontend는 dist/를 서빙. / → dist/index.html; 그 외 경로는 dist/ 아래로 매핑 (startsWith(DIST_DIR)로 ../ 탈출 차단 + 확장자별 Content-Type), 없으면 index.html로 폴백. dist/가 아직 없으면 "npm run dev 쓰라"는 안내 반환(개발에선 Vite가 UI 담당, 이 서버는 /api 만).
  • handleFile의 핵심은 경로 탈출 방지: path.basename(name)이 디렉터리 부분을 제거해 ../../etc/passwd가 downloads/를 벗어날 수 없음. 이어서 stat 후 Content-Disposition: attachment(UTF-8 파일명 → 한글 제목 안전)와 fs.createReadStream(file).pipe(res)(스트림이라 80MB mp4도 메모리에 안 올림).

5. 다운로드 스크립트 (download.sh)

vanilla 버전과 동일 — 앱은 이걸 블랙박스로 취급(인자 3개 입력, 파일 출력, 성공 시 exit 0). 서버는 bash download.sh "<URL>" "<mp3|mp4>" "<OUTDIR>"로 호출. set -euo pipefail 아래 $OUTDIR/%(title)s.%(ext)s에 씀:

  • MP3 — bestaudio를 추출/재인코딩해 64K MP3.
  • MP4 — ≤1440p 최고 영상 + 최고 오디오를 mp4로 병합(ffmpeg).
  • --no-mtime가 출력 타임스탬프를 "지금"으로 설정 → §4.4의 새 파일 탐지가 신뢰성 있게 동작.

서버는 스크립트의 규약에만 의존하므로, 여기 플래그를 바꿔도 server.ts는 건드릴 필요 없음.

6. 개발 vs 운영

  • 개발(npm run dev): concurrently로 두 프로세스 — Vite 127.0.0.1:5173(React 핫리로드)와 API 서버 5174(PORT=5174 tsx watch server/server.ts). vite.config.ts가 /api/*를 5173 → 5174로 프록시해 브라우저는 그냥 fetch("/api/...")(CORS 불필요). App.tsx 수정은 즉시 반영, server.ts 수정은 tsx watch가 API 재시작.
  • 운영(npm run build → npm start): build가 두 tsconfig를 타입체크하고 앱을 dist/로 번들; start가 tsx server/server.ts를 실행해 dist/ 와 /api를 한 포트(5173)에서 서빙. VPS(PLAN §9)가 nginx 뒤에서 돌리는 게 바로 이것.

7. 설계 결정 한눈에

  • React + TypeScript, Vite 빌드. 타입 있는 컴포넌트 UI + 핫리로드 — 빌드 단계와 node_modules가 그 비용(v2의 의도된 트레이드).
  • 운영에선 한 서버가 정적+API 둘 다. 별도 정적 호스트 없이 server.ts가 dist/와 /api를 함께 → 배포는 여전히 "nginx 뒤 프로세스 하나".
  • 127.0.0.1 바인딩. 앱은 공개 면이 아님; VPS에선 nginx가 TLS 종료 + 비번 강제 + 리버스 프록시.
  • 스트리밍 응답 = 로그. POST 응답 하나가 실시간 로그이고 마지막 줄이 결과 — WebSocket/폴링 불필요.
  • 구조적 보안. 인자배열 spawn(주입 불가), 호스트 화이트리스트(SSRF 불가), 파일 서빙의 path.basename(경로 탈출 불가), 4KB 본문 제한, 작업 직렬화.

8. 실행

# 사전 준비 (macOS)
brew install yt-dlp ffmpeg node

# JS 의존성 1회 설치
npm install

# 핫리로드 개발 (Vite + API)
npm run dev          # → http://127.0.0.1:5173

# 또는 운영 빌드를 로컬에서
npm run build && npm start   # → http://127.0.0.1:5173

페이지를 열고, 유튜브 링크를 붙여넣고, MP3/MP4를 고른 뒤 Download. 로그가 실시간으로 흐르고, 파일은 downloads/에 떨어지며 브라우저 다운로드가 자동 시작됩니다.

VPS에서 HTTPS + 비밀번호 뒤에 두는 방법은 PLAN.md §9(Phase B) 참고.
