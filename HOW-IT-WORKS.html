How it works

ytdown — How This App Is Built

A walkthrough of how ytdown is actually implemented, based on the code as it stands. Where PLAN.md describes what to build and how to deploy it, this document explains how the working app fits together — the request flow, each file's job, and the design decisions behind them.

The app is a React + TypeScript single-page UI (built with Vite) talking to a small TypeScript Node server. The server runs your yt-dlp command, streams the live log back to the browser, and hands you the finished file.

Where this fits in the 3-phase plan: this walkthrough describes Phase 1 — the local browser + server app, the part that exists today. Phase 2 (a macOS native app via Tauri, reusing this same React UI through a Rust backend) and Phase 3 (the VPS deploy) are described in PLAN.md. This document will gain a Phase-2 section once that app is built; for now it documents the working Phase-1 code.

1. The big picture

Browser (React SPA) ──POST /api/download {url,format}──▶  Node server (server.ts, 127.0.0.1)
   ▲                                                          │ spawn("bash", [download.sh, …])
   │  live log (streamed response body)                       ▼
   │                                                      download.sh ──▶ yt-dlp + ffmpeg
   │                                                          │            → downloads/<title>.<ext>
   └──GET /api/file/<name> (attachment)◀──────────────────────┘  final "__FILE__ <name>" line = result

One request does the whole job. The server streams yt-dlp's output straight into the HTTP response as it runs, and the last line of that stream is a sentinel — __FILE__ <name> (success) or __ERROR__ <message> (failure). The browser reads the stream live, then parses that final line. The browser never talks to YouTube; only the server does (through your script).

Dev vs production is the one wrinkle (§6): in dev, Vite serves the React app with hot-reload and proxies /api/* to the Node server; in production, Vite builds to dist/ and the same Node server serves those static files and the API.

3. The frontend (React + TypeScript)

3.1 Entry: index.html → main.tsx

index.html is almost empty — just <div id="root"></div> and the module script. main.tsx finds that div and mounts the app with createRoot(...).render(<StrictMode><App /></StrictMode>). The ! is a non-null assertion (the root div always exists); StrictMode only affects development.

3.2 State: App.tsx

The UI is one component. Everything that can change on screen is React state (useState) — because setting state is what tells React to re-render: url, format (typed "mp3" | "mp4"), busy, log, and a status object.

3.3 The submit handler

handleSubmit is async (it awaits the network stream): preventDefault → reset state → fetch("/api/download") → if not ok, throw the body text → read the streamed body incrementally with getReader() + TextDecoder in a for (;;) loop, appending to log → match the accumulated text against the __FILE__ / __ERROR__ sentinels → finally re-enables the button. JSX renders conditionally ({status && …}, {log && <pre>…}).

4. The server (server/server.ts)

Plain node:http in TypeScript (run by tsx, no compile step), bound to 127.0.0.1 only.

Method & pathHandlerWhat it does
POST /api/downloadhandleDownloadvalidate → serialize → run → stream log
GET /api/file/<name>handleFilestream a finished file as a download
GET <else>serveFrontendserve the built SPA from dist/
  • One job at a time: a busy flag → 429 while a job runs (2 GB RAM target; clean log).
  • Validation: isValidYouTubeUrl() requires https: + a host allowlist; format ∈ {mp3, mp4}. Body capped at 4 KB. All before spawning.
  • Run + stream: snapshot downloads/ → spawn("bash", [SCRIPT, url, format, dir]) (args array → no shell injection; via bash so the shebang/pipefail apply) → pipe stdout/stderr to the response → on exit 0, the newest new file is the result (__FILE__ <name>).
  • Serve file: path.basename(name) blocks path traversal; Content-Disposition: attachment (UTF-8 filename); piped with createReadStream (an 80 MB MP4 never sits in memory).

5. The download script (download.sh)

The app treats it as a black box: three args in, a file out, exit 0. It runs under set -euo pipefail and writes to $OUTDIR/%(title)s.%(ext)s. MP3 = bestaudio → 64K mp3; MP4 = ≤1440p video + best audio merged; --no-mtime sets the output time to "now" (which makes the newest-file detection reliable). Change any flag here without touching server.ts.

6. Dev vs production

  • Dev (npm run dev): concurrently runs Vite on 5173 (React + hot-reload) and the API on 5174 (tsx watch); vite.config.ts proxies /api/* → 5174, so the browser just calls fetch("/api/...").
  • Production (npm run build → npm start): typecheck + bundle to dist/, then tsx server/server.ts serves dist/ and /api on one port. This is what the VPS (PLAN §10) runs behind nginx.

7. Design decisions

  • React + TypeScript, Vite-built. A typed, component-based UI with hot-reload — at the cost of a build step + node_modules.
  • One server for static + API in prod. Deployment is "one process behind nginx".
  • Bind to 127.0.0.1. The app is never the public face; on the VPS, nginx terminates TLS + enforces the password.
  • Streaming response as the log. The single POST response is the live log; its last line is the result — no WebSocket/polling.
  • Security by construction. Args-array spawn, host allowlist, path.basename, a 4 KB body cap, serialized jobs.

8. Running it

brew install yt-dlp ffmpeg node
npm install
npm run dev                  # → http://127.0.0.1:5173  (hot-reload)
# or the production build:
npm run build && npm start    # → http://127.0.0.1:5173

Paste a link, pick MP3/MP4, hit Download. The log streams live; the file lands in downloads/ and the browser download starts automatically. For HTTPS + a password on a VPS, see PLAN.md §10 (Phase 3). For the upcoming native app, see §9 (Phase 2).
